# AI Agent Starter Kit

FastAPI-based starter project for building an MVP from `ai_agent_template`.

The starter kit uses:

- Claim Agent SDK
- Synthetic tool plugins
- RAG-ready keyword policy retriever
- SQLite local runtime storage
- Customer and reviewer prototype screens
- Reviewer queue, reviewer action history, retrieval logs, and audit logs
- Deterministic confidence plus LLM-assisted explanation confidence fields

## Local Run

```text
cd ai_agent_template/developer_kit/sdk
python -m pip install -e .

cd ../starter_kit
python -m pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

The Starter Kit bootstraps the repository root onto `sys.path`, so the command above works from the `starter_kit` directory.

Alternative run from the repository root:

```text
python -m uvicorn ai_agent_template.developer_kit.starter_kit.app.main:app --reload --port 8000
```

FastAPI is intentionally listed as a starter dependency, not a template dependency.

## Implemented API Surface

- `POST /claims`
- `GET /claims`
- `GET /claims/{claim_id}`
- `POST /reviews`
- `GET /reviews/queue`
- `GET /reviews/{claim_id}`
- `POST /reviews/{claim_id}/rerun`
- `POST /reviews/{claim_id}/actions`
- `GET /reviews/{claim_id}/actions`
- `GET /reviews/{claim_id}/audit-logs`
- `POST /evaluations/runs`
- `GET /configs/model`

`/reviews` responses expose `output` as the canonical review object and also include `agent_output` for backward compatibility.

## Model Provider

The default active provider is `mock` so local smoke tests run without network access. To exercise the configured OpenAI-compatible model, edit:

```text
ai_agent_template/developer_kit/starter_kit/config/model_config.yaml
```

Set:

```text
active_provider: general_llm
```

The `general_llm` entry is configured with:

```text
provider_type: openai_compatible
base_url: https://m2.geniemars.kt.co.kr:10601/v1
model_id: gemma-4-26B-4aB-it
```

The workflow keeps deterministic tool/rule decisions authoritative. The model may improve reviewer-facing summary, notes, evidence clarity, judgment difficulty, and uncertainty explanation.

## Fraud_Check Integration

The default Starter Kit `plugins.yaml` uses the synthetic fraud checker so local demos do not require Fraud_Check to be running.

To test the remote Fraud_Check integration, run with:

```powershell
$env:CLAIM_AGENT_PLUGIN_CONFIG = "C:\Users\PC\AA\Automated_Claims_Processing\ai_agent_template\developer_kit\starter_kit\config\plugins.remote.yaml"
$env:FRAUD_CHECK_URL = "http://127.0.0.1:8010"
$env:FRAUD_CHECK_API_KEY = "optional-token"
```

`plugins.remote.yaml` configures:

```yaml
fraud_signal_checker:
  module: ai_agent_template.developer_kit.plugins.remote_fraud_signal_checker
  class: RemoteFraudSignalCheckerPlugin
```

Fraud_Check local defaults:

```powershell
$env:FRAUD_CHECK_URL = "http://127.0.0.1:8010"
$env:FRAUD_CHECK_API_KEY = "optional-token"
```

The plugin calls:

```text
POST /v1/fraud/check
timeout: 3000ms
```

If Fraud_Check returns `fraud_suspected=true`, the claim review workflow routes the claim to `human_review`. If Fraud_Check is stopped, times out, returns HTTP errors, returns invalid JSON, or violates the response contract while remote mode is enabled, the tool returns `status=failed` and the workflow fail-closes to `human_review`. The synthetic fraud plugin remains the default local/demo implementation and is not used as a fallback for remote failures.

## RAG-ready Path

The Starter Kit injects `KeywordPolicyRetriever` into `WorkflowRunner` when policy chunks can be built from the template's data generator candidates. If retrieval is unavailable, `policy_search` falls back to the existing synthetic policy basis.

## Medical Registry Seed

The Template can load synthetic KCD/EDI registry rows generated by `data_generator` into the local SQLite database:

```powershell
python -m ai_agent_template.developer_kit.starter_kit.app.db.seed_medical_registry --generated-dir data_generator\generated
```

Loaded tables:

- `medical_code_registry`
- `procedure_code_registry`
- `diagnosis_treatment_rules`
- `medical_routing_rules`
- `medical_registry_seed_runs`

These rows are synthetic development data. For real insurer or production use, verify the official KCD and EDI distribution path, license terms, effective dates, and redistribution restrictions before import. Do not include restricted real code tables in this repository.

During review execution, `RuntimeMedicalRegistryService` queries these registry tables and merges KCD/EDI candidates, diagnosis-treatment relation rules, and insurer medical routing rules into the workflow payload's `medical_evidence`. The stored claim payload is preserved and evaluation labels are never loaded into this runtime path.

To import insurer-approved KCD/EDI/routing rule files:

```powershell
python -m ai_agent_template.developer_kit.starter_kit.app.db.import_official_medical_registry `
  --kcd-file C:\approved_sources\kcd.csv `
  --edi-file C:\approved_sources\edi.csv `
  --routing-rules-file C:\approved_sources\insurer_medical_routing_rules.json `
  --version official-2026.1 `
  --effective-from 2026-01-01 `
  --license-note "Approved internal import; do not redistribute source tables."
```
